# Lotes GitHub — confiabilidade (19/10/2026)

## Contexto
O Worker encaminha as ferramentas oficiais GitHub e Cloudflare, sem copiar os servidores. `push_files` pode demorar mais que 45 s; existem ocorrencias reais de operacao incerta perto desse limite. Outra limitacao potencial e o volume de argumentos enviados pelo ChatGPT. Nenhum desses sintomas, isoladamente, demonstra que a gravacao falhou.

## Ajustes
- Operacoes GitHub `push_files` e `create_or_update_file`: 90 s para `tools/call`, 100 s para o `fetch` upstream. Consultas e Cloudflare mantem 45 s na chamada e 55 s no transporte; DELETE permanece 5 s. O handshake continua com 15 s.
- `push_files`: checagem local **antes** do envio ao provedor: no maximo **8 arquivos** e **128 KiB** na codificacao UTF-8 de `arguments`. Se ultrapassar, o MCP retorna `BATCH_TOO_LARGE` sem executar escrita; dividir no cliente em commits menores, preferencialmente em branch, e verificar cada commit antes do proximo. Para arquivo unico maior, avaliar `create_or_update_file`.
- Logs sem nome de ferramenta nem conteudo: tamanho da entrada em bytes, contagem de arquivos para `push_files`, classificacao de lote, resultado, tempo, provedor, traceId. Nao armazenar codigo, paths, tokens, argumentos, SQL ou resultados privados.
- Nao dividir automaticamente um `push_files`: isso transformaria um commit atomico em diversos commits parciais. Nao repetir automaticamente escritas: em timeout o servidor remoto pode ter registrado a alteracao.

## Testes e limites do aceite
- Testes Node: orcamento de tempo por ferramenta, calculo UTF-8, limites de contagem, privacidade dos metadados e chamada direta.
- Workerd: chamada `push_files` valida com dois arquivos; lote com nove arquivos recusado localmente (o upstream nao recebe); mantidos testes de leitura JSON/SSE, autenticacao, erro simulado de escrita e nao repeticao.
- `npm run check`, `npm run test:browser`, `npm run test:runtime`, CI na branch e na main, comparacao de 15 bindings e validacao pos-deploy com leituras reais.
- **Aviso:** o prazo da plataforma cliente (ChatGPT) nao e configuravel por este Worker. Mesmo com 90 s internamente, uma operacao pode terminar no GitHub depois de o cliente desconectar. Uso real exige reconciliacao quando houver resposta incerta.
- Manter JavaScript puro (ES Modules), um Worker e nenhuma mudanca em D1, secrets, OAuth ou escopos.

## Fluxo seguro
1. Organizar os arquivos por um mesmo proposito, em branch de trabalho.
2. Dividir chamadas acima de 8 arquivos/128 KiB (nao enviar alteracoes muito grandes num unico pedido ao ChatGPT).
3. Para cada envio, confirmar resposta e SHA do commit; depois consultar o GitHub para validar o estado.
4. Se a resposta for `TIMEOUT` ou `UNCONFIRMED`, **consultar a branch/arquivo e o historico de commits antes de qualquer nova escrita**.
5. Fundir na main apenas apos os testes; registrar publicacao e rollback.
